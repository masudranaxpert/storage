# Fragmented MP4 playback research (2026-10-21)

## Question
Why does a single-file fMP4 (commit `5a42fff`, `+delay_moov+default_base_moof+global_sidx`, `-frag_duration 2000000`) leave `<video src>` spinning on a 2.18 GB / 2h51m file?

## Verified facts (measured, not assumed)
- The served file is a valid fMP4: `ftyp, moov(2 KB), sidx x3, moof/mdat...`; ffprobe duration 10308.5 s. `moov+sidx` total ~126 KB.
- Server side is healthy: Range returns 206, 128 KB in ~1 s, ~2 MB/s. Cloudflare reports `DYNAMIC` (not cached, file > 512 MB free limit).
- The first 40 MB of the same file plays instantly from localhost, with or without the embedded `text` (mov_text) track, so content and codecs are fine.
- Remote `<video src>` never reached `loadedmetadata` in 45 s. The pane issued 141 strictly sequential range requests, each ~0.58 s (one Cloudflare to VPS round trip).
- Local range server with 0.5 s injected latency, same 40 MB content, time to `loadedmetadata`:

| Variant | ffmpeg movflags | loadedmetadata |
|---|---|---|
| A | `+faststart` (non-fragmented) | 0.5 s (1 request) |
| B | `frag_keyframe+empty_moov+default_base_moof` | 6.1 s |
| C | B `+global_sidx` | 7.2-7.8 s |
| D | C `+skip_trailer` (no mfra) | 7.2 s |
| E | D `+delay_moov` | 7.3 s |
| F | video-only, single sidx, `skip_trailer` | 6.7 s |
| G | no sidx, `-frag_duration 60 s` | 5.7 s |

- Request log for variant C: first `bytes=<EOF-32K>-` (trailer probe), then `2424832-`, `6619136-`, `11173888-`, ... a ~4.4 MB stride through the whole file before metadata is reported. Cost scales with file size x RTT.

## Conclusions
1. fMP4 does play in `<video src>` on Chrome, Firefox, Safari. The "browsers cannot play fMP4" claim is false.
2. Chrome's native (FFmpeg) demuxer scans fragments of a fragmented file before reporting metadata. No muxer flag combination we tried (sidx, mfra, delay_moov, fragment length) removes the scan. The delay is RTT-bound, so it grows with file size and distance.
3. Plain faststart MP4 needs one request, but its `moov` for a 2h51m file was ~13 MB (35 s on a slow link).
4. dash.js plays only `.mpd`; it never accepts a single `.mp4` URL.

## Literature
- Same symptom reported: Chrome takes 10-20 s on fMP4 and requests many fragments while Firefox starts in under 1 s ([mediamtx discussion #3906](https://github.com/bluenviron/mediamtx/discussions/3906)); maintainer workaround was serving a standard MP4.
- Chromium handles a `sidx` fragment index as complete only in specific layouts; a 2020 patch added the `sidx` + `mfra` case ([ffmpeg-devel patch](https://ffmpeg.org/pipermail/ffmpeg-devel/2020-August/268067.html), crbug 1107130). Our test with `mfra` still scanned, so this does not rescue the case on current Chromium.
- HLS byte-range fMP4: one file, `#EXT-X-MAP:URI,BYTERANGE` for the init, `#EXT-X-BYTERANGE` per segment; ffmpeg `-hls_segment_type fmp4 -hls_flags single_file` ([overview](https://command-tab.com/2026/08/14/single-file-http-live-streaming/)). Known ffmpeg bugs with negative byte ranges ([#7021](https://trac.ffmpeg.org/ticket/7021)), so the playlist should be generated by our own code from the `sidx`.
- DASH on-demand: `SegmentBase` + `indexRange` over a single file with a global `sidx` ([Cast docs](https://developers.google.com/cast/docs/mpl/streaming_protocols), [Shaka SegmentBase](https://ott.dolby.com/OnDelKits_dev/shaka-player-dlb/shaka-player/docs/api/lib_dash_segment_base.js.html)).

## Options
1. **Keep the fMP4 file, add an HLS byte-range playlist generated in Go from the existing `sidx`/`moof` offsets; play with hls.js (native HLS on Safari).** No scan, instant start, seeks fetch only needed segments. Recommended.
2. Keep the fMP4 file, add a DASH `SegmentBase` MPD (dash.js is already in the player). Same benefit; needs MPD generator.
3. Revert to faststart MP4. Simple, but a ~13 MB `moov` for long titles.

## Round 2: HDD and fast-start constraints (2026-10-21)

Constraints from the owner: (1) the HDD suffers from many small files and many requests; (2) start and seek must be as fast as possible.

### Measured on the real file (first 4 MB, `sidx` parsed)
- 5154 fragments, avg 2.00 s, avg 413 KB, max 543 KB, every fragment starts with a SAP (keyframe). Audio and video share one `moof/mdat` per fragment. Average bitrate ~1.7 Mbps.
- Consequence: a segment index needs no remux. HLS segments are contiguous byte runs of N fragments taken from the `sidx`.

### Prototype (local range server, 0.5 s injected latency per media request, 210 s test clip)
| Player | Time to first frame |
|---|---|
| native `<video src>` fMP4 | 5.7-7.8 s |
| hls.js, byte-range playlist, 6 s segments (first 2 are 2 s) | playlist 0.5 s, metadata 1.55 s, **playing 1.6 s** |
| hls.js, seek to 150 s | playing again in ~0.5 s |
- 37 segments of ~1.1 MB for 6 s grouping; 106 for 2 s grouping. All reads are contiguous ranges of one file.

### HDD analysis
- The HDD cost is head seeks, not request count. One file read in large contiguous ranges is the cheap pattern; thousands of small segment files are the expensive one (inode + scattered extents). Byte-range HLS keeps the single file.
- Chrome's progressive `<video>` already issues a range request every ~4.4 MB (see the request log). 6 s HLS segments at 1.7 Mbps are ~1.3 MB, so request rate is the same order, not higher.
- Concurrent viewers on one HDD are the real risk: N viewers means N read positions. Mitigations: 6-10 s segments (>=1 MB per read), 1-4 MB kernel/`posix_fadvise` readahead, rely on page cache for hot titles, promote hot titles to the SSD tier (existing lifecycle engine), cap concurrent streams per node.

### Fast-start levers
1. Generate the playlist in Go from the `sidx` and return it inline with the playback ticket response (saves one round trip). Cache parsed `sidx` per file (126 KB for this title) in memory or a small sidecar.
2. First two segments short (2 s), later ones 6-10 s.
3. `EXT-X-MAP` init is ~2 KB; keep it as one tiny range request.
4. Avoid ffmpeg `-hls_flags single_file` ([trac #7021](https://trac.ffmpeg.org/ticket/7021) negative byte ranges); our own writer is ~100 lines.
5. Multi-audio titles already produce separate `.m4a` files; they need a master playlist with `EXT-X-MEDIA` audio groups.
